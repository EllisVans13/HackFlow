1. ЧТО ТАКОЕ HACKFLOW

HackFlow — сайт, на котором можно организовать работу студенческого хакатона: зарегистрироваться, собрать команду, выбрать кейс, вести задачи, общаться, изучать материалы, следить за расписанием, сдать проект и получить результат.

Кейс — это задача, которую предлагают решить участникам. Например, придумать сервис для студенческого кампуса.

Сайт объединяет работу нескольких людей. Поэтому он должен не только красиво показывать страницы, но и запоминать действия, проверять права пользователей и одинаково рассчитывать результаты.

Исходный код — это набор текстовых файлов с инструкциями для компьютера. Компьютер выполняет эти инструкции и получает работающий сайт.

Программный проект также содержит картинки, шрифты, настройки запуска, инструкции для разработчиков и автоматические проверки.


2. ТРИ ГЛАВНЫЕ ЧАСТИ САЙТА

В HackFlow есть три основные части.

Первая — интерфейс, или frontend. Это всё, что человек видит в браузере: кнопки, меню, карточки, формы, домики, цвета и сообщения об ошибках.

Вторая — серверная часть, или backend. Она получает действия пользователя и решает, можно ли их выполнить. Например, имеет ли человек право открыть чужой проект или успел ли капитан сдать работу до дедлайна.

Третья — база данных. В ней сохраняются пользователи, команды, задачи, сообщения, оценки и другие сведения.

Удобная аналогия — библиотека:

— интерфейс — стойка, через которую читатель делает запрос;
— серверная часть — библиотекарь, который проверяет запрос и выполняет его;
— база данных — систематизированный каталог и записи о книгах и читателях.

Общая схема работы:

Пользователь нажимает кнопку
→ браузер отправляет запрос серверу
→ сервер проверяет данные и права
→ читает или изменяет записи в базе
→ отправляет ответ браузеру
→ интерфейс показывает результат.

Сервер — это программа, работающая на компьютере, который принимает запросы. При публичном размещении этот компьютер находится у хостинг-провайдера. При локальном запуске им становится ваш собственный ноутбук.


3. НА КАКИХ ЯЗЫКАХ НАПИСАН ПРОЕКТ

JavaScript используется в интерфейсе. На нём описано, что должно происходить после нажатия кнопки, выбора темы или открытия раздела.

Python используется на сервере. На нём написаны правила работы команд, проверка доступа, сохранение данных, расчёт оценок и создание дипломов.

CSS используется для оформления. Он задаёт цвета, размеры, отступы, расположение блоков, тени и поведение интерфейса на узком экране.

HTML описывает структуру веб-страницы: заголовки, поля ввода, кнопки и другие элементы. В нашем интерфейсе значительная часть этой структуры описана внутри React-компонентов с помощью JSX.

JSX — удобная запись структуры интерфейса рядом с JavaScript. Файлы с расширением .jsx содержат такую запись. Перед публикацией специальные инструменты превращают её в обычные файлы, понятные браузеру.

SQL — язык запросов к базе данных. Разработчикам не приходится вручную писать каждый SQL-запрос: во многих местах это делает библиотека SQLAlchemy.


4. КАК УСТРОЕН ИНТЕРФЕЙС: REACT

Для интерфейса используется React 19.

React — библиотека для создания веб-интерфейсов. Библиотека — готовый набор полезных инструментов, который подключают к своему проекту, чтобы не писать всё с нуля.

Главная идея React — компоненты. Компонент можно представить как самостоятельную деталь конструктора: карточку команды, окно оценки, меню, аватар или целую страницу.

Например, компонент переключателя тем умеет:
— показать текущую тему;
— раскрыть список вариантов;
— обработать выбор;
— закрыть список;
— отобразить состояние сохранения.

Другие части интерфейса могут использовать эту готовую деталь, не повторяя весь её код.

React хранит состояние интерфейса. Состояние — это информация, которая нужна странице прямо сейчас: какое окно открыто, что введено в поле, загружены ли задачи, какую тему выбрали.

Когда состояние меняется, React обновляет соответствующие элементы страницы. Например, после успешной загрузки задач вместо надписи «Загрузка» появляются карточки.

В коде часто встречаются названия:

useState — инструмент для хранения состояния компонента.
useEffect — инструмент, который запускает связанные с компонентом действия: например, загрузку данных или периодическое обновление чата.
props — данные, которые один компонент передаёт другому. Например, имя пользователя и ссылку на аватар.

Изучать эти названия наизусть для понимания проекта не требуется. Важно понимать: интерфейс состоит из деталей, а данные определяют, что эти детали показывают.

Основная связь частей интерфейса находится в frontend/src/main.jsx. Там собраны вход, навигация, загрузка общих данных, многие страницы и общие элементы. Отдельные крупные возможности вынесены в соседние файлы.


5. КАК ПОЛУЧАЮТСЯ ЦВЕТА, ТЕМЫ И МОБИЛЬНАЯ ВЕРСИЯ

Главные стили находятся в frontend/src/style.css.

В проекте подключён Tailwind CSS 4. При этом большая часть конкретного оформления HackFlow задаётся собственными CSS-правилами в style.css.

В CSS используются переменные цветов. Это значения с понятным назначением: фон страницы, фон карточки, основной текст, граница, акцентный цвет.

Когда пользователь выбирает тему, интерфейс переключает набор этих значений. Поэтому кнопки, меню и карточки меняют оформление согласованно.

В проекте есть три темы:
— чёрно-жёлтая: графитовые поверхности и тёплые жёлтые акценты;
— фиолетовая: светлые поверхности и фиолетовые акценты;
— новогодняя: сливочные поверхности, клюквенные акценты и праздничный декор.

Переключатель описан в frontend/src/ThemeSwitcher.jsx. Выбранная тема сохраняется в профиле пользователя на сервере.

Снег, гирлянда и другие праздничные элементы находятся в frontend/src/Snowfall.jsx. Снежинки имеют разные размеры, начальные позиции, скорости и боковое движение. Состояние переключателя снега сохраняется в браузере этого устройства.

Иконки берутся из Lucide React. Это готовый набор значков: календарь, чат, настройки, выход, колокольчик и другие.

Адаптивность означает, что один интерфейс подстраивается под размер экрана. В CSS есть правила, которые меняют число колонок, размеры и поведение меню на телефоне.

Отдельные приложения для Android и iPhone в этом репозитории не реализованы. Пользователь открывает тот же сайт в браузере телефона или компьютера.


6. ДЛЯ ЧЕГО НУЖНЫ VITE, NODE.JS И NPM

Vite 6 — инструмент разработки и сборки интерфейса.

Во время разработки он помогает быстро видеть изменения. При подготовке сайта к размещению он собирает исходные файлы в готовый комплект для браузера.

Сборка — это преобразование множества исходных файлов в подготовленные HTML, JavaScript и CSS. Готовый результат появляется в папке frontend/dist.

Node.js — среда, в которой работают инструменты сборки JavaScript. В нашем проекте она нужна прежде всего для инструментов интерфейса. Основная серверная логика сайта написана на Python и Flask.

npm — программа, которая устанавливает JavaScript-библиотеки и запускает команды из настроек проекта.

frontend/package.json содержит список библиотек и команды: например, сборку сайта и проверки интерфейса.

frontend/package-lock.json фиксирует конкретные версии устанавливаемых зависимостей. Это помогает получать одинаковую установку на разных компьютерах.

Зависимость — сторонняя библиотека, которую использует наш код. React и Lucide — примеры зависимостей.


7. КАК УСТРОЕНА СЕРВЕРНАЯ ЧАСТЬ: PYTHON И FLASK

Сервер написан на Python. Для организации веб-приложения используется Flask 3.1.

Flask — каркас приложения, или framework. Он помогает принимать запросы по адресам, вызывать нужный код и возвращать ответы.

Например, запрос «покажи задачи команды» и запрос «создай задачу» могут относиться к одному разделу, но выполнять разные действия.

Flask связывает конкретный адрес и действие с конкретной Python-функцией.

Функция — именованный набор инструкций. Если представить проект как сборник рецептов, функция — один рецепт: что взять, что проверить, что сделать и что вернуть.

В backend/hackflow/__init__.py находится create_app. Эта функция собирает приложение: читает настройки, подключает базу, вход пользователей, защитные механизмы и разные группы адресов.

backend/wsgi.py создаёт готовое приложение, которое затем запускает серверная программа.

Большая часть основных действий сайта находится в backend/hackflow/api.py. В нём описаны регистрация, команды, задачи, сообщения, материалы, расписание, сдача и другие операции.

Часть функций вынесена в отдельные модули: так проще находить и менять связанные правила.

Модуль — обычный файл с кодом, посвящённый определённой части проекта.


8. ЧТО ТАКОЕ API И КАК ЧАСТИ САЙТА ОБЩАЮТСЯ

API — согласованный способ, которым интерфейс обращается к серверу. Для пользователя это скрытая часть работы сайта.

У нашего API адреса начинаются с /api.

Пример адреса:
/api/teams/7/tasks

Он означает обращение к задачам команды с идентификатором 7. Идентификатор, или id, — уникальный номер записи.

Сам адрес не говорит всего о действии. В запросе также указывается способ обращения:

GET — получить данные.
POST — отправить действие; часто используется для создания записи.
PATCH — изменить часть данных.
DELETE — удалить запись.

Например, GET для адреса задач запрашивает список, а POST передаёт новую задачу. Конкретное значение каждого действия определяется серверным кодом.

Браузер отправляет запросы с помощью fetch. В main.jsx есть общая функция api, которая добавляет нужные заголовки, передаёт данные и обрабатывает ответы сервера.

Обычно данные передаются в JSON. Это текстовый формат с названиями полей и их значениями. Например, у задачи могут быть название, ответственный и срок.

Сервер возвращает не готовую фотографию страницы, а данные. React использует их, чтобы нарисовать интерфейс.

Если действие невозможно, сервер возвращает сообщение об ошибке. Например: «Ответственный должен состоять в команде».

Знакомые разработчикам числа в ответе имеют определённый смысл:
— 200 — запрос успешно выполнен;
— 401 — требуется вход;
— 403 — нет права выполнить действие;
— 404 — запись или адрес не найдены;
— 409 — действие конфликтует с текущими данными или состоянием;
— 429 — слишком много запросов за короткое время.


9. ПРИМЕР: ЧТО ПРОИСХОДИТ ПОСЛЕ «СОЗДАТЬ ЗАДАЧУ»

Шаг 1. Пользователь открывает форму и вводит название, описание, ответственного и, при необходимости, срок.

Шаг 2. Интерфейс собирает введённые значения и отправляет запрос на адрес задач конкретной команды.

Шаг 3. Сервер определяет, кто отправил запрос и к какой команде относится действие.

Шаг 4. Сервер проверяет права и данные. В частности, назначенный ответственный должен состоять в этой команде.

Шаг 5. Сервер создаёт запись Task и сохраняет изменения в базе.

Шаг 6. Сервер возвращает список задач. Интерфейс использует ответ и обновлённые данные, чтобы показать карточку на доске.

Позже пользователь меняет статус задачи. Сервер сохраняет новый статус, после чего можно заново рассчитать прогресс команды.

Закрытие вкладки не удаляет сохранённую задачу: она уже находится в базе данных.

Этот пример показывает важное разделение: интерфейс показывает действие, сервер проверяет и выполняет его, база сохраняет результат.


10. КАК ХРАНЯТСЯ ПОЛЬЗОВАТЕЛИ, КОМАНДЫ И ЗАДАЧИ

Основная база данных проекта — PostgreSQL. В Docker-конфигурации используется PostgreSQL 17.

Базу можно представить как набор связанных таблиц. Таблица похожа на электронную таблицу, но система дополнительно умеет связывать записи, ограничивать неверные изменения и обрабатывать запросы разных пользователей.

Некоторые основные сущности:

User — пользователь: email, ник, роль, тема и другие сведения профиля.
Hackathon — хакатон: название, описание, сроки, состояние и правила.
Case — кейс, который может выбрать команда.
Team — команда: название, капитан, выбранный кейс и оформление дома.
Membership — запись о членстве человека в команде.
Task — задача с ответственным, сроком и статусом.
Message — сообщение в определённом командном канале.
Material — учебный материал.
Schedule — событие расписания.
Submission — отправленный командой проект.
JuryScore — оценка жюри.
PeerAssignment — назначение проекта команде для взаимной проверки.
PeerReview — отправленная командная оценка.
PersonalResult — личный результат участника после публикации итогов.
AwardCertificate — запись о выданном дипломе.
Notification — уведомление.

Эти описания находятся в backend/hackflow/models.py.

Модель — описание того, какие поля есть у записи и как она связана с другими записями. Например, задача хранит номер команды, а членство связывает номер человека с номером команды.

Для работы Python с базой используется SQLAlchemy и её интеграция Flask-SQLAlchemy. Этот инструмент переводит действия с моделями в запросы к базе.

Ограничения существуют также на уровне самой базы. Например, один человек не должен одновременно состоять в двух командах одного хакатона. Это проверяется не только кнопками интерфейса.

В упрощённом локальном режиме используется SQLite. Она хранит базу в отдельном файле на компьютере. Такая база не синхронизируется автоматически с PostgreSQL на Render.


11. ЧЕМ БАЗА ДАННЫХ ОТЛИЧАЕТСЯ ОТ ХРАНИЛИЩА ФАЙЛОВ

База хранит организованные записи. PDF-презентации, ZIP-архивы, аватары и пользовательские обложки сохраняются отдельно, в файловом хранилище сервера.

В базе остаётся информация о файле: кому он принадлежит, для чего загружен и под каким внутренним именем лежит.

Например, у отправленного проекта есть запись о PDF-презентации, а сами байты PDF находятся в папке загрузок.

Это объясняет, почему для рабочего сайта нужны и база, и сохранное файловое хранилище. Наличие записи в базе ещё не означает, что соответствующий файл физически лежит на сервере.

При загрузке аватара библиотека Pillow открывает изображение, проверяет формат и размеры, уменьшает его и пересохраняет. В профиле сохраняется ссылка на обработанный файл.

Библиотека — готовый инструмент. Pillow специализируется на работе с изображениями.


12. КАК РАБОТАЮТ ВХОД И ПРАВА ДОСТУПА

Регистрация создаёт пользователя. Вход подтверждает, что человек знает пароль от существующего аккаунта.

Пароль сохраняется в виде специального проверочного значения — хеша. Werkzeug помогает создать это значение и проверить введённый пароль. Сайт не должен хранить исходный пароль обычным текстом.

После входа браузер получает cookie с данными, позволяющими продолжить сессию. Сессия — период работы пользователя после авторизации, когда не требуется заново вводить пароль для каждого действия.

Flask-Login помогает серверу понимать, какой пользователь обращается к нему сейчас.

Роли определяют доступные возможности:

Участник работает в своей команде и участвует в хакатоне.
Капитан управляет составом и выполняет действия от команды, например сдаёт проект. Капитанство хранится у команды, а не является отдельной глобальной ролью аккаунта.
Организатор управляет назначенным мероприятием.
Жюри оценивает назначенные работы.
Ментор читает пространство назначенных команд и даёт рекомендации.
Эксперт изучает назначенные решения и оставляет обратную связь.
Администратор управляет пользователями, ролями и другими настройками платформы.

Права могут зависеть от конкретного хакатона. Человек, назначенный жюри одного события, не получает автоматически доступ ко всем проектам всех событий.

Код сервера проверяет права при каждом защищённом действии. Скрыть кнопку недостаточно: пользователь может попытаться отправить запрос самостоятельно.

Дополнительные защитные инструменты:

Flask-WTF и CSRF-токен — помогают отличать предусмотренные сайтом запросы на изменение данных от поддельных запросов с посторонней страницы.

Flask-Limiter — ограничивает количество повторных действий, например попыток входа.

Flask-Cors — задаёт разрешённые адреса, с которых браузер может обращаться к API в разных конфигурациях запуска.

Проверка файлов и полей — ограничивает размер загрузки, допустимые форматы, длину текста и диапазоны оценок.

AuditLog — журнал важных действий. Он помогает понять, кто и что менял.

Наличие этих механизмов не является обещанием абсолютной безопасности. Это конкретные реализованные меры защиты.


13. КАК РАБОТАЮТ ЧАТ, ОБУЧЕНИЕ И РАСПИСАНИЕ

Чат.
Сообщение отправляется на сервер и сохраняется в базе вместе с автором, командой и временем. Интерфейс периодически запрашивает сообщения — сейчас примерно раз в пять секунд. Это обычное обновление запросами, без отдельной системы WebSocket.

Есть командный канал и отдельный диалог капитана с организатором. Для них действуют разные проверки доступа.

Обучение.
Учебные карточки хранят название, тему, формат, описание и ссылку. В интерфейсе можно искать и фильтровать материалы, открывать их и отмечать изучение. Отметка сохраняется для конкретного человека.

Внешние видео и статьи обычно размещены на сторонних ресурсах. HackFlow организует доступ к ним и хранит прогресс; собственный видеохостинг в проекте не создаётся.

Расписание.
Сервер хранит название события, дату, время, длительность, описание, спикера и ссылку. Интерфейс показывает календарь и список событий.

Можно указать Zoom, Яндекс Телемост, обычную ссылку или офлайн-формат. Организатор создаёт онлайн-комнату в выбранном сервисе и вставляет её адрес. HackFlow сохраняет расписание, но не создаёт эту комнату автоматически через Zoom или Телемост API.

Выгрузка ICS — это файл календаря, который можно открыть в поддерживающем его календарном приложении.


14. КАК СТРОЯТСЯ ДОМИКИ КОМАНД

Город команд — наглядное представление прогресса.

Серверная логика находится в backend/hackflow/city.py. Он смотрит на сведения команды и рассчитывает, какое состояние нужно показать.

В текущем коде:
— команда без выбранного кейса получает участок;
— после выбора кейса, пока задач нет, показывается фундамент;
— когда появились задачи, начинается состояние строительства;
— после отправки проекта показывается состояние «проект сдан».

Процент прогресса рассчитывается так:

количество выполненных задач / общее количество задач × 100.

Например, если выполнены 3 задачи из 10, прогресс равен 30%.

Число уровней дома зависит от доли выполненных задач. Интерфейс получает эти значения и рисует соответствующий дом.

Изображения строятся с помощью SVG. Это описание линий, фигур, цветов и координат. Такие рисунки удобно масштабировать без обычного размытия маленькой картинки.

За интерфейс города отвечают TeamCity.jsx, BuildingScene.jsx, CityBuildings.jsx и CabinBuildings.jsx.

Доступны варианты архитектуры: башня, лаборатория, А-фрейм и дом на дереве. Оформление выбирает капитан.

Рост дома показывает выполнение отмеченных задач. Он сам по себе не доказывает качество проекта и не является оценкой жюри.


15. КАК УСТРОЕНЫ СДАЧА, ЖЮРИ И PEER REVIEW

Капитан отправляет итоговый проект: название, описание, GitHub, ссылку на продукт и PDF-презентацию. ZIP исходников можно приложить отдельно.

Перед сдачей сервер проверяет необходимые поля, выбранный кейс, принадлежность файла команде и дедлайн. Отправка сохраняется в Submission. Повторная итоговая отправка ограничена правилами серверной реализации.

Для анонимной проверки организатор подготавливает отдельное описание и PDF, убирая сведения об авторах. Сервер очищает часть служебной информации PDF. Библиотека pypdf используется для чтения и пересохранения таких документов.

Имена и контакты, напечатанные прямо на страницах PDF, организатор должен убрать самостоятельно. Автоматического понимания всех человеческих имён код не обещает.

Жюри получает назначенные анонимные работы и ставит баллы по критериям. Сумма максимальных баллов критериев — 100.

Peer review — взаимная оценка командами. В новом формате каждой команде назначаются три чужих проекта, а каждый проект должен получить оценки трёх других команд.

Нужны минимум четыре команды со сданными и подготовленными проектами. Собственную работу оценивать нельзя. Если условия для распределения не выполнены, сервер сообщает об этом, вместо того чтобы незаметно менять правила.

Организатор переводит подготовленное мероприятие на этап проверки, после чего сервер распределяет работы. Члены команды могут читать назначенные материалы, а общую оценку с обоснованием отправляет капитан. Повторная оценка той же работы от команды запрещена.

В текущем main для хакатонов с включённым новым форматом используется формула:

Итог = 0,8 × средняя оценка жюри + 0,2 × средняя оценка трёх команд.

Пример: жюри поставило в среднем 90, команды — в среднем 80.
Итог: 0,8 × 90 + 0,2 × 80 = 72 + 16 = 88 баллов из 100.

Оценки жюри и команд сначала выставляются по шкале до 100. Веса 80% и 20% применяет сам сервер.

Публикация результатов не разрешается, пока не завершены необходимые проверки. Старые мероприятия могут сохранять прежний режим, в котором официальный результат определяется жюри: переход на новую схему не должен произвольно менять архив.

Основные файлы: peer_assessment.py, peer_api.py, services.py, api.py и frontend/src/PeerReview.jsx.


16. ЧТО ДЕЛАЕТ CODECHECK

CodeCheck помогает обратить внимание на сходство кода в отправленных проектах одного хакатона.

Он читает ZIP с исходниками, выбирает подходящие программные файлы и приводит часть содержимого к общему виду. Например, различия только в именах переменных становятся менее значимыми.

Затем алгоритм сравнивает последовательности элементов кода. Используется SequenceMatcher из стандартной библиотеки Python.

В отчёте могут отображаться показатель сходства и совпадающие фрагменты. Сам показатель не означает «столько процентов проекта украдено».

У анализа есть ограничения по файлам, объёму кода и времени. Система сообщает, если не может провести полную проверку или если исходники не загружены.

Загруженный код не запускается. Проверка не ищет совпадения по всему интернету, не определяет авторство ChatGPT и автоматически не снижает оценку.

Окончательное решение принимает жюри. Общие шаблоны, учебные примеры и стандартные конструкции могут быть похожи без нарушения правил.

Главный файл анализа — backend/hackflow/plagiarism.py. Связанные функции чтения архива находятся в services.py. Отображение отчёта описано в frontend/src/CodeReport.jsx.

Отдельно используется GitHub API: сайт может проверить доступность указанного публичного репозитория и наличие README. Для этих HTTP-запросов на сервере используется библиотека requests. Это отдельная проверка, а не поиск плагиата в GitHub.


17. КАК ПОЯВЛЯЮТСЯ РЕЗУЛЬТАТЫ, УРОВНИ И ДИПЛОМЫ

После завершения необходимых проверок организатор публикует результаты.

Сервер рассчитывает места и сохраняет персональный результат для каждого участника команды.

Опыт, или XP, зависит от итогового балла и сложности:
— лёгкий хакатон: итоговый балл × 0,7;
— средний: итоговый балл × 1,5;
— сложный: итоговый балл × 2,4.

Например, результат 88 на среднем хакатоне даёт 132 XP.

Опыт завершённых одобренных хакатонов суммируется. Уровень определяется порогами: 0, 250, 700, 1400, 2500, 4000 и 6000 XP.

Участники команд на 1, 2 и 3 месте получают персональные дипломы после публикации официальных итогов.

В базе создаётся запись диплома: получатель, команда, мероприятие, место, дата и идентификатор проверки. Сам PDF формируется при открытии или скачивании на основе сохранённых сведений.

ReportLab — библиотека, которая рисует PDF: размещает текст, рамки, цвета, шрифты и QR-код. В проект включены шрифты для кириллицы.

QR-код содержит ссылку на публичную проверку документа и связанные результаты. Он помогает узнать, актуален ли документ. Это не квалифицированная электронная подпись.

Повторная публикация не должна создавать копии тех же наград. Если после апелляции изменилось место, старый документ может быть отозван, а новый — выдан автоматически.

Основные файлы: certificates.py, certificate_pdf.py, certificate_api.py и frontend/src/AwardCertificates.jsx.


18. ЧТО ТАКОЕ ФОНОВЫЕ ЗАДАЧИ И УВЕДОМЛЕНИЯ

Некоторые действия происходят не после нажатия кнопки, а по времени. Например, напоминание о приближающейся сдаче.

Для этого есть отдельная программа backend/hackflow/worker.py. Её часто называют worker — фоновый исполнитель.

Она примерно раз в минуту проверяет сроки и создаёт внутренние уведомления:
— когда до сдачи осталось не больше 24 часов;
— когда скоро начинается вебинар, консультация или практикум.

Код старается не создавать повторные одинаковые напоминания.

Worker должен быть запущен в используемой конфигурации размещения. Само наличие его файла ещё не означает, что он запущен на конкретном сервере.

Внутреннее уведомление показывается в сайте. Отправка настоящего электронного письма — отдельная возможность, которая требует почтового сервера и его настроек.

SMTP — способ общения приложения с почтовым сервером. В проекте почта используется, в частности, для восстановления пароля. Без соответствующей настройки письмо отправляться не будет.


19. КАК ОБНОВЛЯЕТСЯ СТРУКТУРА БАЗЫ

При развитии сайта появляются новые поля и таблицы. Например, для обезличенного PDF или длительности встречи.

Такие изменения описаны в миграциях: backend/migrations/versions/.

Миграция — инструкция, как привести структуру существующей базы к новой версии. Она отличается от полного удаления базы и создания её заново.

Для миграций используются Flask-Migrate и Alembic.

Например, миграция может добавить поле, не удаляя существующих пользователей. Но сохранность конкретных изменений всё равно проверяют тестами и резервными копиями: один только термин «миграция» не является гарантией.

В проекте есть несколько исторических ветвей миграций и инструкции их объединения. Поэтому актуальную структуру нужно получать штатной командой обновления, а не вручную угадывать таблицы.


20. КАК ПРОЕКТ ЗАПУСКАЕТСЯ НА КОМПЬЮТЕРЕ И В ИНТЕРНЕТЕ

Упрощённый локальный запуск.
Скрипт scripts/start_local.py готовит окружение, собирает интерфейс, обновляет отдельную SQLite-базу и запускает приложение. Это удобный режим для знакомства с проектом на своём компьютере.

Запуск через Docker.
Docker упаковывает программу вместе с необходимой средой. Так меньше различий между установками на разных компьютерах.

Dockerfile — рецепт сборки. В нашем проекте сначала собирается интерфейс с помощью Node.js, затем создаётся среда Python для сервера.

compose.yaml — описание того, как совместно запускать несколько служб. В конфигурации есть приложение, PostgreSQL, Redis, обновление базы и фоновая программа напоминаний.

Redis здесь используется для общих счётчиков ограничений запросов. Основные задачи, сообщения и пользователи хранятся в PostgreSQL.

Gunicorn принимает веб-запросы и передаёт их приложению Flask. Это программа для запуска Python-веб-приложения на сервере.

Для размещения на собственном сервере предусмотрен Caddy. Он может принимать HTTPS-запросы и передавать их приложению. Такой посредник называется обратным прокси.

Render — облачный сервис, на котором можно разместить сайт и базу. Он предоставляет публичный адрес, доступный другим пользователям.

render.yaml описывает вариант создания служб Render. В этой конфигурации есть PostgreSQL и постоянный диск для загрузок. Выбранные в файле ресурсы платные; это настройка предлагаемого размещения, а не доказательство тарифа уже существующего стенда.

backend/start_render.py подготавливает окружение, применяет миграции, при нужных условиях создаёт начальные аккаунты и демоданные, затем запускает сайт и включённые напоминания.

Есть также backend/hackflow/render_start.py — другой предусмотренный способ запуска вручную настроенного Docker-сервиса Render. Какой вариант работает на конкретном стенде, зависит от настройки этого сервиса.

Перезапуск приложения не должен сам по себе стирать данные: база и файловое хранилище должны быть подключены как сохраняемые ресурсы.


21. ДЛЯ ЧЕГО НУЖНЫ НАСТРОЙКИ ОКРУЖЕНИЯ

Некоторые значения нельзя жёстко вписывать в общедоступный код: адрес рабочей базы, секрет сессии, почтовые настройки.

Они передаются через переменные окружения, а локально могут храниться в файле .env.

Например:

DATABASE_URL — где находится база и как к ней подключиться.
SECRET_KEY — секретное значение для защиты подписанных данных сессии и связанных механизмов.
PUBLIC_URL — публичный адрес сайта, в том числе для ссылок в QR-кодах.
UPLOAD_FOLDER — папка загруженных файлов.
COOKIE_SECURE — нужно ли отправлять cookie только через HTTPS.

В тексте выше перечислены названия настроек, а не их реальные секретные значения.

python-dotenv помогает читать локальные настройки из .env.

requirements.txt содержит список Python-библиотек. pip — программа, которая устанавливает эти библиотеки. Для JavaScript похожую задачу выполняет npm.

Виртуальное окружение Python — отдельный набор установленных библиотек для проекта. Оно помогает не смешивать зависимости разных программ на одном компьютере.


22. КАК ПРОВЕРЯЕТСЯ КОД

В backend/tests/ находятся автоматические серверные тесты. Они создают контролируемые ситуации и сравнивают фактический ответ с ожидаемым.

Например, тест может проверить:
— участник может создать задачу своей команды;
— чужая команда не получает её сообщения;
— после дедлайна нельзя сдать проект;
— нельзя оценить собственную работу;
— итог правильно учитывает веса 80/20;
— повторная публикация не дублирует дипломы;
— миграция сохраняет существующие записи.

Тесты запускаются инструментом pytest.

Во frontend/scripts/smoke.mjs находятся проверки рендеринга интерфейса. Рендеринг — получение структуры страницы из React-компонентов. Такие проверки помогают заметить, если компонент перестал собираться или потерял ожидаемую часть содержимого.

Они не заменяют настоящую проверку браузером: для неё нужно отдельно нажимать кнопки, открывать окна и смотреть отображение на разных экранах.

В .github/workflows/ci.yml описан автоматический запуск проверок через GitHub Actions. Когда соответствующий workflow выполняется после отправки изменений или создания запроса на объединение, GitHub запускает серверные тесты и проверки сборки интерфейса.

Наличие workflow не означает, что можно объявить любой новый коммит проверенным: нужно смотреть результат конкретного запуска.

Сборка и тесты проверяют разные вещи. Успешная сборка говорит, что файлы удалось подготовить для запуска. Она сама по себе не доказывает, что все пользовательские сценарии правильные.

24. ЧТО ЗНАЧАТ MAIN, КОММИТ И РЕПОЗИТОРИЙ

Репозиторий — хранилище исходников с историей изменений. В нашем случае оно находится на GitHub.

Git — инструмент ведения этой истории.

Ветка — отдельная линия разработки. В main находится основная версия проекта. Другие ветки позволяют готовить изменения отдельно.

Коммит — сохранённый набор изменений с идентификатором. По нему можно понять, какую именно версию мы обсуждаем.

Переключение локальной ветки выбирает файлы другой версии на компьютере разработчика. Оно само по себе не переключает базу на другой набор пользователей и не обновляет публичный сайт.

Публичный сайт обновляется после развёртывания. На хостинге может быть включено автоматическое развёртывание новых коммитов выбранной ветки, но это определяется настройками хостинга.


25. КАК ЧИТАТЬ НАШ ПРОЕКТ В ПЕРВЫЙ РАЗ

Не нужно начинать с чтения всех файлов подряд.

Сначала откройте README.md и сам сайт. Посмотрите, какие страницы и действия вообще существуют.

Затем выберите один небольшой сценарий — например, создание задачи.

Найдите на стороне интерфейса страницу доски в main.jsx. Посмотрите, какие поля передаются при создании задачи.

После этого найдите серверную функцию tasks в api.py. Посмотрите, какие условия она проверяет.

Далее найдите Task в models.py. Так станет понятно, что сохраняется.

В конце посмотрите тесты соответствующего поведения. В них видно, какой результат разработчики считают правильным.

Такой путь удобнее, чем пытаться сразу понять каждую строчку: одно действие → интерфейс → запрос → сервер → база → ответ.


26. КОРОТКОЕ ОБЪЯСНЕНИЕ ДЛЯ ЗАЩИТЫ ПРОЕКТА

«HackFlow состоит из интерфейса, серверной части и базы данных. Интерфейс написан на JavaScript с использованием React, а оформление задаётся CSS и Tailwind. Сервер написан на Python и Flask: он проверяет права, выполняет действия и рассчитывает результаты. Данные хранятся в PostgreSQL, с которой код работает через SQLAlchemy. Части приложения обмениваются запросами через API. Для запуска предусмотрены Docker и размещение на Render. В проекте реализованы командная работа, обучение, расписание, анонимное оценивание, город команд и автоматические дипломы. Корректность проверяется автоматическими тестами и проверками интерфейса».
