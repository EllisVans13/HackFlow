# HackFlow

HackFlow — веб-платформа для проведения студенческих хакатонов: команды, задачи, обучение, расписание, коммуникации, сдача проектов и проверка работ в одном пространстве.

**Публичный сайт:** https://hackflow-4oyo.onrender.com/  
**Репозиторий:** https://github.com/EllisVans13/HackFlow  
**Основная ветка:** `main`. Проверка кода и передача отчётов жюри включены в основную ветку.

На бесплатном Render первый запрос после простоя может открываться с задержкой. Работоспособность соединения с PostgreSQL можно проверить по [/api/health](https://hackflow-4oyo.onrender.com/api/health): успешный ответ содержит `status: "ok"` и `database: "postgresql"`. Это проверка соединения, а не всех пользовательских сценариев.

## Возможности

- **Пространство хакатона:** описание, правила, кейсы, критерии, материалы, расписание, дедлайны и команды. Закрытая информация доступна после регистрации на конкретное мероприятие либо сотрудникам с соответствующими правами.
- **Участие:** самостоятельная регистрация на одобренные хакатоны с открытым сроком регистрации; параллельное участие в нескольких мероприятиях. Также сохранены ручной допуск и импорт email из CSV.
- **Команды и менторы:** отдельный аккаунт ментора, выбор капитаном и назначение организатором; ментор читает пространство только назначенных команд и оставляет рекомендации. Создание команды участником, код приглашения, заявки, персональные приглашения зарегистрированным участникам, передача капитанства. Ограничение одной команды на хакатон проверяется сервером и базой.
- **Kanban:** задачи с описанием, ответственным и сроком; статусы «К выполнению», «В работе», «На проверке», «Выполнено»; прогресс рассчитывается по выполненным задачам.
- **Общение:** сохранённая история командного чата, авторы, время, аватары и уведомления; отдельный канал капитана с организатором.
- **Обучение:** материалы со ссылками, темами и форматами, отметки изучения, личный прогресс и статистика организатора.
- **Расписание:** встречи с датой, временем, длительностью, сервисом (Zoom / Яндекс Телемост / ссылка / офлайн), описанием и спикером; создание, изменение и удаление организатором, календарь и экспорт ICS.
- **Сдача:** капитан отправляет название, описание, PDF-презентацию, GitHub и ссылку на продукт; ZIP исходников необязателен. Сохраняются время и отправленные материалы. Поддерживается одна итоговая отправка; после дедлайна сервер отклоняет сдачу.
- **Проверка проектов:** назначение экспертов и жюри, рекомендации, анонимная версия для жюри, анонимный Peer Review трёх команд, итог из 100 по формуле 80% жюри + 20% среднего Peer Review, публикация результатов и апелляции.
- **Уведомления:** приглашения и вступление, сообщения, материалы, изменения расписания, сдача, обратная связь и результаты. Напоминания о сдаче и скором начале событий требуют работающего фонового процесса.
- **Дополнительные функции:** уровни участников, «Город команд», PDF-дипломы призёрам с QR-проверкой, загрузка аватаров и обложек, три темы оформления.

## Оценка проекта: 80% жюри и 20% Peer Review

**Peer Review доступен только зарегистрированным участникам выбранного хакатона, включая капитанов.** Организатор, администратор, жюри, ментор и эксперт не получают участнический раздел, доступ к заданиям и отправке оценок Peer Review. Управление назначениями доступно организатору своего мероприятия и администратору. Участие в другом мероприятии не открывает этот раздел. Читать назначенные работы могут члены команды, отправлять единую оценку — только капитан. Публичные официальные итоги остаются доступны всем.

Для новых хакатонов официальная оценка — **из 100 баллов**:

```text
итог = 0,8 × средняя оценка жюри + 0,2 × средняя оценка трёх команд
```

Жюри и каждая команда используют критерии с суммой максимум 100; система применяет веса сама. Пример: 90 от жюри и среднее 80 от команд → **72 + 16 = 88**. В рейтинге видны вклад жюри (до 80), вклад Peer Review (до 20) и итог. XP уровня = итоговый балл × коэффициент сложности: 0,7 / 1,5 / 2,4. Итог 88 даёт соответственно 61,6 / 132 / 211,2 XP.

Каждой команде по возможности назначаются **три другие команды для проверки её проекта**, и каждая команда по возможности проверяет **проекты трёх других команд**. Самооценка и повторная оценка одной работы запрещены. Для такой схемы нужны минимум четыре команды со сданными проектами; три команды могут дать каждой работе только две чужие рецензии.

Порядок работы:

1. Капитаны сдают проекты до дедлайна. Организатор подготавливает обезличенный текст и отдельный PDF каждой работы.
2. Организатор подготавливает материалы в своём кабинете, открывает вкладку **«Проекты» → в карточке проекта «Назначить Peer Review» → выбирает команду-рецензента** (либо использует общий запуск «Назначить проекты командам») (или переводит мероприятие в статус **«На проверке»**). Сервер автоматически назначает каждой команде три чужих проекта. Распределение сохраняет существующие назначения; повторный перевод не создаёт копий. Отдельного участнического раздела Peer Review у сотрудников нет: организатор управляет подготовкой и запуском проверки из своего кабинета. Кнопка вызывает POST /api/hackathons/:id/review-assignments и передаёт выбранные team_id и submission_id. Собственная команда и команды без отправленного проекта не предлагаются. Панель и кнопка видны также у мероприятий со старой схемой; после официальной публикации кнопка видна, но заблокирована с объяснением причины. Для ранее открытых вкладок поддерживаются прежние адреса назначения; выбранная команда учитывается при полном распределении, а публикация проходит все проверки официальных итогов.
3. Капитан открывает **Peer Review**, читает назначенные анонимные работы, открывает/скачивает PDF и выставляет баллы с обоснованием. Остальные члены команды могут просматривать материалы, итоговую рецензию отправляет капитан.
4. Организатор публикует официальный итог в кабинете организатора. Сервер не разрешит публикацию, пока у каждой работы не будет трёх командных оценок и всех назначенных оценок жюри.
5. После публикации сохраняются итоговые результаты, рассчитываются места/XP и выдаются дипломы команд 1–3 мест. Повторная публикация не дублирует награды. Апелляция с изменением оценки жюри пересчитывает итог с теми же весами и сохранёнными оценками команд.

**Анонимность:** рецензентам передаются код проекта, проверенный организатором текст и отдельный PDF. Не передаются авторы, название команды, оригинальные файлы или ссылки GitHub. Метаданные, аннотации и дополнительные действия PDF очищаются; имена/контакты в видимом тексте должен удалить организатор и подтвердить это при загрузке. После выставления оценок подмена обезличенных материалов запрещена.

Миграция `a18_peer_meetings` сохраняет уже опубликованные результаты и прежние начатые Peer Review без произвольного пересчёта. Новые хакатоны, подготовленные ещё не оцениваемые мероприятия и новый демосценарий используют 80/20. Архивные события прежней схемы явно помечаются как без вклада Peer Review.

## Встречи: Zoom и Яндекс Телемост

Организатор или администратор с правами на мероприятие открывает **«Расписание» → «Создать встречу»**. Поля: название, описание, дата/время, длительность 5–1440 минут, сервис, ссылка подключения, спикер и тип события. Время вводится в часовом поясе браузера, сохраняется в UTC и показывается в местном времени; календарный экспорт содержит начало и окончание.

В форме есть прямые ссылки на [главную Яндекс Телемоста](https://telemost.yandex.ru/) и [Zoom](https://zoom.us/). Организатор создаёт комнату в своём аккаунте сервиса и вставляет **ссылку подключения**, а не адрес главной страницы. HackFlow сохраняет встречу и уведомляет участников. Автоматического создания внешней комнаты по API без сервисных учётных данных нет. Ссылки проверяются на соответствие выбранному сервису; для офлайн-события подключение не требуется.

## Зачем нужны эксперты

**Эксперт** изучает назначенный отправленный проект и оставляет рекомендации по реализации и улучшению. Его комментарии видит команда. **Ментор** сопровождает назначенную команду по ходу работы, читает её рабочее пространство и консультирует. **Жюри** анонимно оценивает работы по критериям. Официальный вклад в итог дают жюри и Peer Review, экспертные рекомендации не прибавляют баллы автоматически. Роли эксперта и ментора назначает администратор, работы эксперту и команды ментору — организатор.

## Проверка кода на заимствования и передача отчёта жюри

**CodeCheck сравнивает исходники отправленных проектов внутри одного хакатона.** Капитан загружает ZIP при сдаче. Анализ не выполняет загруженный код и не отправляет его внешним сервисам.

Организатор открывает **«Управление» → «Проекты» → «Проверить код»**. Отчёт автоматически рассчитывается и при назначении проекта жюри. Назначенное жюри получает внутреннее уведомление и видит раздел **«Проверка кода на заимствования»** в своей анонимной карточке проекта:

- статус и время проверки;
- максимальное сходство пары файлов в процентах;
- количество сравнённых проектов и файлов;
- анонимные коды совпавших работ и нормализованные фрагменты;
- ограничения анализа и причины пропуска недоступных исходников.

При открытии работы жюри автоматически получает актуальный отчёт; устаревшая проверка пересчитывается. Можно нажать **«Обновить проверку»** принудительно. Если после анализа сдан новый проект, прежний отчёт помечается устаревшим. Повторная проверка того же набора исходников с тем же статусом не дублирует уведомление. Фамилии, email, названия команд, имена файлов, GitHub и исходные ссылки не передаются жюри в этом отчёте; текст фрагментов нормализован. Доступ к чужим неназначенным работам запрещён сервером.

Идентификаторы, строки и числовые литералы нормализуются, затем сравниваются последовательности токенов. Это помогает находить копии после переименования переменных и замены констант. Зависимости и каталоги сборки исключаются. Анализ ограничен восемью поддерживаемыми файлами из каждого ZIP, 2000 токенами на файл и мягким бюджетом около трёх секунд на запрос. При усечении показывается **частичный анализ**, а не заявление о полной проверке. Процент означает максимальное сходство пары файлов, **не долю плагиата во всём проекте**.

Без ZIP — «Исходники недоступны»; при отсутствующем/повреждённом файле — ошибка анализа; без другого доступного ZIP — «Недостаточно проектов для сравнения». Эти состояния не выдаются за «0% плагиата». Поддерживаются `.py`, `.js`, `.jsx`, `.ts`, `.tsx`, `.java`, `.go`, `.c`, `.cpp`, `.rs`; файлы короче 40 нормализованных токенов или больше 256 КБ исключаются. Архив ограничен 1000 записями и 20 МБ после распаковки.

Подсказки отчёта: высокое сходство — от 80%, среднее — от 50%, низкое — ниже 50%; это не пороги автоматических санкций. Общие шаблоны могут давать высокий процент: результат — сигнал для решения жюри, а не доказательство плагиата. Автоматических санкций и изменения баллов нет. Поиск по всему интернету, внешним базам и определение процента ИИ-кода не подключены. Отдельный worker для проверки кода не нужен, в том числе на бесплатном Render.

Реализация: [plagiarism.py](backend/hackflow/plagiarism.py), нормализация ZIP в [services.py](backend/hackflow/services.py), проверки доступа в [api.py](backend/hackflow/api.py). Отчёты хранятся в существующей таблице `code_report`; новая миграция не требуется.

## Роли и блокировка пользователей

| Роль | Доступные действия |
|---|---|
| Участник | Регистрация на мероприятия, команда, задачи, чат, обучение, просмотр результатов и своих дипломов |
| Капитан | Статус внутри команды: приглашения, решения по заявкам, выбор кейса, передача капитанства и итоговая сдача |
| Организатор | Управление назначенными хакатонами: правила, сроки, кейсы, материалы, расписание, команды и доски, назначения экспертов и жюри, проверки и результаты |
| Жюри | Анонимные проекты, назначенные на оценивание; баллы, комментарии и запрос дополнительной проверки |
| Ментор | Отдельный кабинет: назначенные команды, кейсы, состав, задачи и чат в режиме просмотра, сданный проект, материалы, расписание, рекомендации; без участия в командах, сдачи и оценивания |
| Эксперт / ревьюер | Отдельный кабинет назначенных проектов: изучает решение и даёт рекомендации авторам; не выставляет официальные баллы и не участвует как команда |
| Администратор | Пользователи, роли и назначения на хакатоны, блокировка и разблокировка аккаунтов, рассмотрение заявок хакатонов, аудит |
| Главный администратор | Дополнительно передаёт владение другому активному администратору и сам остаётся обычным администратором |

**Блокировка участника реализована у администратора:** «Администрирование» → пользователь → «Заблокировать». Она запрещает вход во всю платформу; загрузчик сессии также отклоняет заблокированного пользователя. Владелец защищён от блокировки через этот API.

**У организатора в текущем `main` нет отдельной функции бана участника или исключения из своего хакатона.** API изменения `blocked` требует административной роли. Организатор может назначать и снимать жюри своего мероприятия, но это отзыв судейских прав, а не бан участника. Это ограничение зафиксировано в [сверке требований](docs/CASE_REQUIREMENTS.md).

## Менторы и русскоязычное обучение

Администратор назначает зарегистрированному пользователю роль **«Ментор»** в таблице пользователей. В публичной регистрации нельзя самостоятельно получить эту роль. Пользователь с незавершённым участием в командах не может одновременно стать ментором. У ментора отдельная навигация и профессиональные поля «Специализация» / «О себе» в настройках; уровни и участническая активность не показываются.

Капитан открывает **«Моя команда» → «Ментор команды» → «Выбрать ментора»**. Организатор открывает **«Участники и жюри» → «Командные доски и консультации» → команда → «Выбрать ментора»**. Доступны активные зарегистрированные аккаунты менторов; Email и опыт в каталоге не раскрываются. У команды один основной ментор, один ментор может вести несколько команд. Капитан и организатор могут сменить или снять назначение до завершения хакатона. Прежний ментор теряет доступ сразу; комментарии сохраняются. История назначений не позволяет затем дать бывшему ментору анонимную проверку знакомого проекта.

Ментор открывает **«Мои команды»**: состав, кейс, задачи, командный чат и отправленный проект доступны для чтения, рекомендации — для отправки. Материалы и расписание открываются только для хакатонов с его назначениями. Он не редактирует задачи, не пишет от имени команды в её чат, не сдаёт решения и не выставляет оценки жюри. Ограничения проверяются на Flask, включая прямые API-запросы.

В §5.3 приложенного кейса перечислены семь допустимых форматов: **видеоуроки, презентации, документы, внешние материалы, вебинары, консультации, задания**; допускается сочетать их. Документ не задаёт конкретных курсов и не ограничивает трек одними видео.

Добавлена подборка из **16 русскоязычных позиций**: 4 видео с авторского канала на Rutube, 10 документов/внешних материалов, учебная презентация HackFlow и практическое задание. Источники — Дока, METANIT, JavaScript.ru, Александр Ламков. [Полный список и границы проверки](docs/LEARNING_SOURCES.md). Кнопки «Смотреть видео», «Открыть презентацию», «Открыть материал», «Подключиться» ведут непосредственно к ресурсу; условие задания доступно в карточке. Есть поиск, фильтры по теме/формату и отметки изучения для участников.

Миграция **`a17_mentors_learning`** автоматически добавляет подборку существующим хакатонам. Новые мероприятия получают её при создании. Повторное добавление не создаёт дубликаты, пользовательские материалы и отметки изучения сохраняются. Только распознанные исходные демопримеры заменяются на русскоязычные аналоги с сохранением ID. Прочие исторические материалы не удаляются и получают язык «не проверен»; организатору нужно проверить их отдельно. Новые материалы публикуются с языком `ru`; это заявление организатора, автоматического распознавания языка видео нет. Для повторного добавления недостающих материалов: `flask --app wsgi seed-learning` (в Compose — через `docker compose exec app`).

Форматы «Вебинар» и «Консультация» поддерживают реальные HTTPS-ссылки подключения, которые задаёт организатор. Выдуманные комнаты и будущие встречи в подборку не добавлены. Новая учебная презентация открывается внутри сайта без внешнего видеохостинга.

## Прошедшие хакатоны и общедоступный рейтинг

Раздел **«Прошедшие хакатоны»** есть у участника, капитана, администратора, организатора, жюри и ментора. Он не требует выбора текущего мероприятия или допуска. На странице входа есть ссылка на публичный архив. После развёртывания обновления прямой адрес текущего стенда: **https://hackflow-4oyo.onrender.com/results**.

При открытии рейтинга из кабинета сохраняются боковое меню и рабочее пространство. Кнопка «Все хакатоны» возвращает в каталог; «Прошедшие хакатоны» — к архиву. Внешние ссылки `/results` и `/results/<id>` остаются отдельными публичными страницами с возвратом на платформу.

В архиве показаны завершённые одобренные мероприятия. Для опубликованных результатов открывается рейтинг: **место, команда, проект, итоговые баллы из 100**, критерии и правило разрешения равенства. Прямую ссылку `/results/<id>` можно отправить любому человеку: аккаунт и участие в хакатоне не нужны. Если результаты ещё не опубликованы, карточка показывает соответствующее сообщение, а публичный API не выдаёт рейтинг.

У администратора, организатора, жюри и ментора из левого меню убран участнический блок **«Итоги хакатона»**. Вместо него для просмотра официальных результатов используется общий архив; рабочие кабинеты и назначенные проверки сохраняются.

Публичный ответ не содержит email, участников команды, кодов приглашения/обезличивания, файлов, исходных ссылок сдачи, переписки или индивидуальных комментариев жюри. Доступ к рейтингу не открывает закрытое рабочее пространство. Отдельные внутренние API управления и предварительного просмотра результатов по-прежнему требуют соответствующих прав. Дополнительная миграция БД для архива не нужна.

## Уровни и результаты

Участник начинает с уровня **0**. Опыт рассчитывается из истории личных результатов завершённых одобренных хакатонов с официально опубликованными итогами:

| Сложность | Коэффициент | Максимум за 100 баллов | За 88 баллов |
|---|---:|---:|---:|
| Лёгкий | ×0,7 | 70 XP | 61,6 XP |
| Средний | ×1,5 | 150 XP | 132 XP |
| Сложный | ×2,4 | 240 XP | 211,2 XP |

Пороги суммарного опыта для уровней 0–6: **0 / 250 / 700 / 1400 / 2500 / 4000 / 6000 XP**. Награда зависит от официального итогового балла и сложности, а не напрямую от места команды. Для новых мероприятий итог = 0,8 × среднее жюри + 0,2 × среднее трёх команд. Каждое начисление XP округляется до двух знаков (половина вверх), затем начисления суммируются. Пересмотр оценки после апелляции или сложности пересчитывает опыт и уровень; отдельная миграция для этого не нужна. У старых мероприятий сохраняется их официальный балл прежней схемы. Опыт вычисляется из данных, поэтому обновление страницы и повторная публикация не добавляют его повторно. Оценки проектов из 100 и командный рейтинг сохраняются отдельно.

Организатор указывает сложность нового хакатона. Администратор может изменить её, одобрить или отклонить заявку. До одобрения регистрация закрыта.

После публикации официальных итогов сервер автоматически выдаёт участникам команд на местах 1–3 персональные дипломы; PDF формируется при просмотре или скачивании. Дипломы доступны в профиле и результатах мероприятия. QR в заново скачанном PDF ведёт на `/results/<id>?certificate=<token>` — публичные результаты нужного хакатона с проверкой конкретного диплома. Подтверждённый документ показывает имя получателя, команду, место, организатора и номер. Отозванный/неизвестный токен не показывает персональные сведения. Старый маршрут проверки `/api/certificates/<token>/verify` продолжает работать и содержит ссылку на результаты. При изменении места старый диплом отзывается и выдаётся новый. В текущем `main` нет автоматического сертификата всем участникам; опубликованные официальные рейтинги завершённых одобренных хакатонов доступны всем по `/results/<id>`, а архив — по `/results`. Неопубликованные рейтинги остаются закрытыми. Публичная проверка конкретного диплома также сохранена.

## Локальный запуск

### Docker и PostgreSQL

Нужны Git, Python 3 и установленный, запущенный Docker с Compose.

```bash
git clone https://github.com/EllisVans13/HackFlow.git
cd HackFlow
git switch main
python3 scripts/start_docker.py
```

Launcher создаёт `.env`, собирает приложение, применяет миграции и подготавливает описанный ниже публичный демосценарий Peer Review. Доступы фиксированы только для новых аккаунтов домена `demo.hackflow.test`; реальные пароли сохраняются. Сайт открывается по адресу **http://localhost:8000**, авторизация через ChatGPT не нужна. Если база уже заполнена, используются прежние аккаунты и пароли.

Ручной запуск без launcher:

```bash
python3 scripts/configure.py
docker compose up --build -d
```

`configure.py` создаёт локальную конфигурацию и не перезаписывает существующий `.env`. Миграционный сервис автоматически добавляет демосценарий Peer Review. Файлы демо сохраняются в том же upload_data, что использует приложение. Для дополнительного прежнего каталога есть отдельный seed-demo. Для их добавления задайте `DEMO_PASSWORD` в локальном `.env`, затем выполните:

```bash
docker compose exec app flask --app wsgi seed-demo
```

После изменения `.env` пересоздайте контейнеры командой `docker compose up -d`, чтобы они получили переменную, и только затем запускайте seed. `seed-demo` добавляет демонстрационный каталог и первого демоадминистратора, если администратора ещё нет. Существующие пароли не меняются. Для отдельного первого полноценного администратора/владельца используйте интерактивную команду (наличие ограниченного демоадминистратора этому не мешает):

```bash
docker compose exec app flask --app wsgi init-admin
```

Восстановление пароля существующего аккаунта:

```bash
docker compose exec app flask --app wsgi reset-password
```

Остановка: `docker compose down`. Не добавляйте `-v`, если хотите сохранить базу и загрузки.

### Простой режим без Docker

Нужны Python 3.12+ и Node.js 22+. В корне проекта:

```bash
python3 scripts/start_local.py
```

На Windows также есть `START-WINDOWS.bat`, на macOS — `START-MAC.command`. Этот режим использует **отдельную SQLite-базу**, автоматически создаёт демоданные и показывает случайный пароль в терминале. Данные и настройки находятся в `.local-data/`. Они не синхронизируются с Docker PostgreSQL или Render. Основной серверный стек — PostgreSQL.

## Новый сайт на Render через Blueprint

[Создать сайт из ветки main](https://render.com/deploy?repo=https://github.com/EllisVans13/HackFlow/tree/main).

Файл `render.yaml` создаёт веб-сервис, PostgreSQL и постоянный диск для загрузок. **Конфигурация платная:** Render показывает стоимость до создания ресурсов. Укажите `ADMIN_EMAIL`; пароли генерируются автоматически. Первый запуск применяет миграции, создаёт администратора и демоданные. Повторные запуски сохраняют аккаунты, результаты и файлы. Локальная база с компьютера автоматически не переносится.

Пошаговая инструкция: [docs/RENDER.md](docs/RENDER.md). Blueprint использует `python start_render.py`; для уже настроенного вручную сервиса сохранён отдельный вариант ниже.

## Размещение на Render

Web Service собирается из `main`, Runtime — Docker, Dockerfile — `./Dockerfile`, Root Directory — пустое поле. **Docker Command:**

```text
python -m hackflow.render_start
```

Команда применяет миграции, идемпотентно готовит новый демосценарий Peer Review и запускает Gunicorn с одним worker. Не оборачивайте её в `sh -c` или кавычки.

| Переменная | Значение |
|---|---|
| `SECRET_KEY` | Собственный постоянный случайный секрет, минимум 32 символа |
| `DATABASE_URL` | Internal Database URL PostgreSQL Render со схемой `postgresql+psycopg://` |
| `COOKIE_SECURE` | `true` |
| `PORT` | `8000` |
| `PUBLIC_URL` | `https://hackflow-4oyo.onrender.com` для текущего стенда |
| `CORS_ORIGINS` | `https://hackflow-4oyo.onrender.com` для текущего стенда |
| `RATELIMIT_STORAGE_URI` | `memory://` для текущего однопроцессного запуска; для нескольких процессов нужен общий Redis |

Render не использует локальную базу автоматически. Аккаунты появляются после seed или отдельного переноса данных. Команда запуска создаёт только явно обозначенные публичные демоаккаунты из таблицы и ограниченного демоадминистратора. Полноценный владелец на ручном сервисе создаётся отдельно; Blueprint использует ADMIN_EMAIL/ADMIN_PASSWORD. Файлы загрузок хранятся отдельно от PostgreSQL; без постоянного диска они могут теряться при перезапусках и развёртываниях. Один дамп БД не переносит PDF-презентации, ZIP и аватары.

Для периодических напоминаний нужен отдельный worker `python -m hackflow.worker` либо внешний планировщик команды `flask --app wsgi reminders`. Обычный Render Web Service запускает только веб-приложение. Наличие worker и постоянного диска зависит от настройки и тарифа; по доступности главной страницы это проверить нельзя.

## Технологии и проверки

Backend: Python, Flask, SQLAlchemy, Flask-Migrate/Alembic, Flask-Login, CSRF и rate limiting. Основная БД — PostgreSQL 17; Redis используется в Compose для общих лимитов. Frontend: React 19, Vite, Tailwind CSS, Lucide. PDF: ReportLab и встроенные шрифты. Видеосервисы и материалы открываются по внешним HTTPS-ссылкам, GitHub API используется для проверки доступности репозитория и README. Собственного видеохостинга нет.

Команды проверки из подготовленного окружения:

```bash
cd backend
python -m pytest -q
cd ../frontend
npm ci
npm run build
npm run test:render
```

По умолчанию серверные тесты используют SQLite. Для PostgreSQL задавайте `TEST_DATABASE_URL` только на отдельную тестовую базу: fixture создаёт и удаляет таблицы. Для изолированных проверок миграций используется `MIGRATION_TEST_DATABASE_URL`, которому нужны права создавать временные схемы. Никогда не запускайте тесты на базе Render или рабочей базе.

Актуальные результаты и границы проверки: [docs/VALIDATION.md](docs/VALIDATION.md). Серверный рендеринг не заменяет проверку браузером; мобильная адаптация есть в CSS, но текущая сверка не подтверждает прохождение всех мобильных сценариев.
